Absolutely. **Person 3 is the database/data-infrastructure owner**, so their job should be defined differently from Person 2.

# 14. STATE INTEGRITY

The database must prevent obviously invalid data.

For example:

A project cannot have:

```text
status = COMPLETED
```

while:

```text
selected_business_organization_id = NULL
```

unless the team has explicitly defined an exception.

Likewise:

A payment should not reference a nonexistent project.

A proposal should not reference a nonexistent business.

A delivery should not reference an unrelated project.

Use:

* Foreign keys
* NOT NULL
* UNIQUE
* CHECK constraints
* Appropriate indexes

where appropriate.

# 36. ROW LEVEL SECURITY

This is one of your **most important responsibilities**.

Enable RLS on application tables where appropriate.

The database must not assume:

> "The backend will always behave correctly."

Defense should exist at multiple layers:

```text

        ↓
Backend authorization
        ↓
Database RLS
```

# 37. RLS EXAMPLES

### NGO

Should only access projects belonging to its organization where appropriate.

### Corporate

Should only access its corporate projects.

### Business

Should only access:

* public opportunities
* its own proposals
* projects where it is the selected business
* its own relevant payment/delivery information

### Admin

Can have broader access.

organization membership
      ↓
organization
      ↓
